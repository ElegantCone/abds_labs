# Лабораторный проект

[![labs](https://github.com/ElegantCone/abds_labs/actions/workflows/energosbyt.energosbyt.lab.yml/badge.svg)](https://github.com/ElegantCone/abds_labs/actions/workflows/energosbyt.energosbyt.lab.yml)

Backend-сервис вымышленной ЖКХ-компании для практики по курсу «Архитектура систем обработки больших данных».

## Схема ClickHouse

DDL-схема находится в [`initdb/001_schema.sql`](initdb/ddl/001_schema.sql). Для таблиц выбраны следующие ключи сортировки и партиционирование:

| Таблица               | `ORDER BY`                                                                                                             | Партиционирование                                                                                       |
|-----------------------|------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| `dim_realty`          | `(address, id)` (бОльшая часть запросов осуществляется по id, сортировка по адресу для легкости алфавитного поиска)    | нет (справочник ограниченного размера)                                                                  |
| `dim_gauges`          | `id` (бОльшая часть запросов осуществляется по id, сортировка по названию для легкости алфавитного поиска)             | нет (справочник ограниченного размера)                                                                  |
| `dim_tariffs`         | `(id, valid_from)` (Для каждого тарифа сохраняются интервальные версии)                                                | нет (справочник ограниченного размера)                                                                  |
| `dim_users`           | `id` (SCD 1 и SCD 3 хранят одну актуальную строку собственника)                                                        | нет (справочник ограниченного размера)                                                                  |
| `fact_gauge_bindings` | `(gauge_id, realty_id)` (Установка и аннулирование с одинаковыми ключом и версией схлопываются)                        | нет (чтобы пара строк всегда могла попасть в одно слияние)                                              |
| `fact_meter_readings` | `(realty_id, gauge_id, reading_date)` (Показание определяется объектом, счётчиком и датой)                             | `toYYYYMM(reading_date)` (Месячные партиции ускоряют работу с периодами и обслуживание старых данных. ) |
| `fact_invoice`        | `(realty_id, created_at, gauge_id)` (Счета добавляются как факты и обычно выбираются по объекту и периоду выставления) | `toYYYYMM(created_at)` (Ограничение объема сканирования по месяцам)                                     |

## Генерация данных

`make gen` создаёт 7 CSV с заголовками в `data/` (папка исключена из git).
Для запуска нужны Java 26, указанная в Gradle toolchain, и `make`; Gradle запускается через Wrapper.
Seed равен 42.

Генератор создаёт 1000 помещений в 4 домах и по 1 собственнику
на помещение, 1100 счётчиков (включая 100 замен у случайно выбранных объектов),
1200 строк привязок, 3 тарифа с 7 версиями каждого и 36000 счетов.
Показания покрывают каждый день с 2023-11-01 по 2026-10-31;
около 3% дат имеют дополнительную корректировку с более поздним `created_at`.

Площади, ФИО, телефоны, модели счётчиков и даты записей различаются.
Потребление учитывает индивидуальный профиль помещения, сезонность и выходные.
Замены происходят 1 числа случайного месяца; накопленные показания нового
счётчика начинаются с 0. Счета выставляются в конце месяца по сумме суточного
расхода и действующей версии тарифа, срок оплаты — 10-е число следующего месяца.

## Загрузка данных

Данные можно загрузить через make:
> make load-datasets

Задача автоматически очистит старые данные и загрузит новые, сгенерированные через 
> make gen
